## 🧭 The Correct Way: Keep `.ts` → Auto-bundle for the browser

The modern way to do this (while keeping `.ts`) is to:

* Keep **source files** as `.ts`.
* Use a **TypeScript-aware dev server (like Vite)** or **build step** to serve transpiled `.js` *in memory*.
* You never touch or commit `.js` — it’s handled automatically.

---

## ✅ Option 1: Use **Vite** (Recommended, Cleanest, Fully TypeScript)

Let’s make your **frontend stay TypeScript**, but make it *runnable* for browsers.

---

### 🧱 Step-by-Step Setup (100% TypeScript Frontend)

#### 1. Install Vite and TypeScript

```bash
cd frontend
npm init -y
npm install vite typescript
```

#### 2. Create a simple `vite.config.ts`

*(Vite supports `.ts` configs!)*

```ts
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    port: 5173,
    proxy: {
      "/api": "http://localhost:3000", // send API calls to backend
    },
  },
});
```

#### 3. Organize your frontend files like this:

```
frontend/
├── index.html
├── src/
│   ├── main.ts
│   ├── alias.ts
│   ├── style.css
│   └── ...
├── vite.config.ts
├── package.json
└── tsconfig.json
```

#### 4. Update `index.html` to use `.ts` directly (Vite handles it!)

```html
<script type="module" src="/src/main.ts"></script>
```

✅ You can now keep:

```ts
// src/alias.ts
export const register = ...
```

No `.js` files anywhere — only `.ts`.

---

#### 5. Add npm scripts (in `frontend/package.json`)

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  }
}
```

---

#### 6. Add `tsconfig.json`

```json
{
  "compilerOptions": {
    "target": "ESNext",
    "module": "ESNext",
    "moduleResolution": "Node",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

---

#### 7. Run it in dev mode

```bash
npm run dev
```

Visit [http://localhost:5173](http://localhost:5173) →
Your TypeScript frontend runs directly, talking to the backend at [http://localhost:3000](http://localhost:3000).

---

#### 8. (Optional) Build for production (still no `.js` in your repo)

```bash
npm run build
```

Vite creates a temporary `/dist` folder with `.js` for browsers —
you **don’t commit that**, you only deploy it.

## ✅ Option 2: Run TypeScript Directly Inside Docker

If your **Dockerfile** serves frontend files (not using Vite dev mode),
you can modify it like this:

```dockerfile
# Build stage
FROM node:18 AS build
WORKDIR /app/frontend
COPY frontend/package*.json ./
RUN npm install
COPY frontend/ .
RUN npm run build  # Vite compiles .ts -> .js (but only inside container)

# Production stage
FROM node:18
WORKDIR /app
COPY --from=build /app/frontend/dist ./frontend
COPY backend ./backend
WORKDIR /app/backend
RUN npm install
CMD ["npm", "run", "start"]
```

You’re still writing **TypeScript**, and `.js` only exists *inside* the container — not in your repo.

---

## 🧩 Summary

| Approach                | Keeps `.ts` only      | Browser works | Auto compile | Docker compatible |
| ----------------------- | --------------------- | ------------- | ------------ | ----------------- |
| **Vite (recommended)**  | ✅                     | ✅             | ✅            | ✅                 |
| Raw `.ts` in `<script>` | ❌                     | ❌             | ❌            | ❌                 |
| Manual `tsc` compile    | ❌ (creates .js files) | ✅             | ✅            | ✅                 |

## 🧠 TL;DR

* Browsers can’t run `.ts`, but Vite transparently compiles it at runtime.
* You can **keep `.ts` in your repo**, **no `.js` files checked in**, and still have data saved to your database.
* Use Vite as your dev/build tool — it’s made for exactly this.

This error message tells us **Docker can’t start your container because port 3000 on your host machine is already in use**.
Here’s what’s happening and how to fix it.

---

### 🔍 **The problem**

```
Bind for 0.0.0.0:3000 failed: port is already allocated
```

That means something else (another container or a process) is already using port 3000 on your system.

---

### 🧰 **Fix options**

#### **Option 1 – Find and stop the conflicting container**

Run:

```bash
docker ps
```

Look for any container mapping port 3000 (e.g. `0.0.0.0:3000->3000/tcp`).

Then stop and remove it:

```bash
docker stop <container_id>
docker rm <container_id>
```

Now restart your stack:

```bash
make all
```

---

#### **Option 2 – Free the port (non-Docker process)**

If a *local process* is using port 3000 (like `node`, `npm run dev`, etc.), find it:

**Linux/macOS**

```bash
sudo lsof -i :3000
sudo kill -9 <PID>
```

**Windows (PowerShell)**

```powershell
netstat -ano | findstr :3000
taskkill /PID <PID> /F
```

Then try again.

---

#### **Option 3 – Change your container’s exposed port**

If you want to keep that other process running, just change your container’s port mapping in your `docker-compose.yml` (or `Dockerfile` if you use `EXPOSE`/`-p` manually).

Example:

```yaml
ports:
  - "3001:3000"
```

Then rebuild:

```bash
docker-compose up --build
```

---

### ✅ **Summary**

| Fix type                          | Command(s)                        |
| --------------------------------- | --------------------------------- |
| Stop conflicting Docker container | `docker ps` → `docker stop <id>`  |
| Kill host process using port      | `lsof -i :3000` → `kill -9 <pid>` |
| Change port mapping               | Edit `ports:` to `3001:3000`      |

Let’s break it down carefully 👇

---

# 🧠 Big Picture

These **three files (`api.ts`, `alias.ts`, and `user.ts`)** work together as a **bridge between your frontend and backend**.

* **`user.ts`** → Backend **Fastify** routes — defines your actual REST API endpoints (server logic + database).
* **`api.ts`** → Frontend **API helper** — defines how your frontend (React/Vue/etc.) calls those backend endpoints.
* **`alias.ts`** → Frontend **form handler** — connects your HTML/JS UI (e.g., a registration form) to the backend via the helper in `api.ts`.

Think of it like this:

```
[User clicks form on frontend]
      ↓
(alias.ts) handles form → calls
      ↓
(api.ts) sends HTTP request → talks to
      ↓
(user.ts) backend route → uses SQLite DB
```

---

# 🔹 1. `user.ts` — the **Backend API (Fastify routes)**

This file runs **on the server (Node.js)**.
It defines all your HTTP endpoints like:

* `POST /register` → create a new user
* `POST /login` → login user
* `POST /user/:id/2fa/setup` → setup two-factor authentication
* `GET /user/:id/friends` → get user’s friends
* etc.

Each route:

* Receives data from the frontend (`req.body` or `req.params`)
* Interacts with your **SQLite database**
* Sends back a JSON response like `{ success: true, userId: 1 }`

✅ Example flow:

```http
POST /api/register
Body: { "username": "alice", "email": "alice@example.com", "password": "1234" }

→ user.ts inserts into the User table
→ returns { success: true, userId: 1 }
```

---

# 🔹 2. `api.ts` — the **Frontend API Wrapper**

This file runs **in the browser**, not the server.

It’s a **helper utility** that knows how to call the backend endpoints you defined in `user.ts`.

It defines reusable functions like:

```ts
export const register = (user) => request("/register", { method: "POST", body: JSON.stringify(user) });
export const login = (user) => request("/login", { method: "POST", body: JSON.stringify(user) });
```

When your frontend app calls `register()`, it internally does:

```http
POST https://localhost:3000/api/register
Content-Type: application/json
Body: { username, email, password }
```

…and waits for the JSON reply from your Fastify backend.

The `request()` function inside `api.ts`:

* Automatically adds headers (like `Content-Type`, JWT `Authorization`)
* Parses JSON
* Throws errors if something fails (`res.ok === false`)

✅ So `api.ts` is your *frontend abstraction* of backend APIs.

---

# 🔹 3. `alias.ts` — the **Frontend Page Script / Form Handler**

This is your **browser-side script** that runs in a webpage.

It directly interacts with the **HTML form** — listens for user input, calls `register()`, and updates the DOM.

Example:

```ts
document.addEventListener("DOMContentLoaded", () => {
  const form = document.getElementById("register-form");
  const message = document.getElementById("register-message");

  form.addEventListener("submit", async (e) => {
    e.preventDefault();
    const username = ...;
    const email = ...;
    const password = ...;

    const res = await register({ username, email, password }); // <-- Calls api.ts
    message.textContent = `✅ Registered successfully! ID: ${res.userId}`;
  });
});
```

✅ `alias.ts` depends on → `register()` from `api.ts`
✅ `api.ts` depends on → backend routes from `user.ts`

---

# 🔁 How They Work Together

Here’s a **visual summary** of the relationships:

```
Frontend (Browser)
 ├── alias.ts (handles DOM, user input)
 │     ↓ calls
 ├── api.ts (fetch wrapper to backend)
 │     ↓ sends HTTP requests
Backend (Fastify Server)
 ├── user.ts (defines routes & DB logic)
 │     ↓ interacts with
 └── SQLite database (User, UserStats, etc.)
```

---

# 🧩 Example Flow: “User Registration”

1. **User fills form** on your webpage → presses Submit
   (handled in `alias.ts`)

2. **`alias.ts`** calls:

   ```ts
   register({ username, email, password });
   ```

   (imported from `api.ts`)

3. **`api.ts`** sends a `POST` request to:

   ```
   https://localhost:3000/api/register
   ```

   (defined in `user.ts`)

4. **`user.ts`** on the server receives it:

   * Hashes the password
   * Inserts user into `User` table in SQLite
   * Returns `{ success: true, userId: 1 }`

5. **Response goes back** to `api.ts`, then `alias.ts`,
   which displays:

   ```
   ✅ Registered successfully! ID: 1
   ```

| File       | Runs Where                | Role                                       | Depends On                   |
| ---------- | ------------------------- | ------------------------------------------ | ---------------------------- |
| `user.ts`  | Backend (Fastify)         | Defines API routes (register, login, etc.) | SQLite DB                    |
| `api.ts`   | Frontend (Browser/Client) | Provides functions to call backend routes  | `fetch`, `user.ts` endpoints |
| `alias.ts` | Frontend (Browser UI)     | Handles HTML form and user interactions    | `api.ts` functions           |

gho_fi5Ru5... (value in the DB) — that's the GitHub access token your server received from GitHub and stored in the OAuth table. It's used by your backend to call GitHub's APIs on behalf of the user.

They should be different — that's expected and correct.
